# 面试题

三十一题，按七类分组。答案都落在这个仓库的代码和实测上；代码位置用「锚点名」标注，学习页会把它变成 GitHub 行号链接（`scripts/learn_anchors.py` 生成）。
最难的问题类（「你遇到过最难的 bug」）链接到 [problems.md](problems.md)。

## 项目概述

### 讲讲这个项目（一分钟版）

**一句话答案**：把一个人工的文档审核流程拆成收件、校验、路由、人工审核、审计几个可以单独测试的服务，Python 和 Java 混合，靠 REST 契约和 SQS 串起来。

**展开**：客户端带幂等键提交文档，文档进 S3，S3 事件触发 Lambda 把它放进 SQS。分发器按 record id 做一致性哈希，交给某一个 worker，同一条记录的步骤在这个 worker 上按版本号顺序执行。worker 校验文件和字段，同步调用 Java 的路由服务拿到队列，再通过 SQS 把任务交给 Java 的审核队列。审核员在 React 页面上认领、通过或驳回，结论通过 outbox 发回 Python，导出成 S3 上的 CSV 和 Parquet。另外做了三件「上线」的事：expand/contract 表迁移、新路由逻辑的分阶段放量和自动回滚、可追踪的状态时间线和告警。

**追问**：这里面你觉得最难的是哪一块？
答：扩容时的所有权交接。一致性哈希只解决「搬得少」，搬的那一瞬间还要靠版本号闸门和带 fencing token 的锁保证不乱序、不并发（锚点 `worker-handle`）。

### 为什么要做成多个服务，而不是一个单体？

**一句话答案**：因为它们变化的节奏和失败的方式不一样，拆开以后每一段可以单独测试、单独扩容、单独失败。

**展开**：收件要一直可用，后面慢了不能拖住它，所以中间隔了 S3 和 SQS。路由规则改得最频繁，还要灰度，所以单独成服务。worker 要按分区横向扩。审核和审计是人用的，和自动化部分的 SLA 不同。每段之间都有契约文件（`contracts/`），两边的测试都读它。

**追问**：拆了之后最大的代价是什么？
答：一条记录的状态散在两边。所以做了合并时间线接口（锚点 `timeline-merge`），并且 trace id 一路透传。

## 设计取舍

### 幂等为什么放数据库，不放 Redis？

**一句话答案**：幂等记录要和业务数据在同一个事务里提交，否则会出现「键记下了、记录没建」或者反过来。

**展开**：`_claim_key`（锚点 `idempotency-guard`）先插入键，插入成功才在同一事务里建记录、写时间线、存响应。失败回滚时键也一起回滚，客户端重试会从头来。Redis 做不到和 Postgres 原子提交。代价是每次提交多一次主键写入，在这个量级可以忽略。

**追问**：两个相同请求同时到会怎样？
答：第二个的插入冲突，`SELECT ... FOR UPDATE` 等第一个提交，然后重放它的响应。测试里八个并发：七个 200 一个 201，库里一条。

### 为什么用 S3 → Lambda → SQS，而不是收件服务直接发 SQS？

**一句话答案**：文件本身才是事实；让「文件到了」这个事件驱动后面的流程，收件服务就只负责可靠地把文件放好。

**展开**：上传放在收件事务里最后一步（锚点 `s3-store`）。Lambda 读对象、算 sha256、记一条时间线、发消息（锚点 `lambda-handler`）。代价是多了一个可能丢事件的环节，所以加了 reconciler：二十秒还在 STORED 的记录直接补发（锚点 `reconciler`）。

**追问**：Lambda 和 reconciler 都发了怎么办？
答：同一个 seq 进队两次，worker 的版本号闸门把第二次当重复丢掉。

### 为什么一致性哈希，不用取模或者共享队列？

**一句话答案**：要保证同一条记录的步骤在同一个 worker 上有序执行，又要让扩容时搬家最少。

**展开**：共享队列谁抢到谁做，同一条记录的步骤会散到不同 worker。取模能固定归属，但扩容几乎全部重排：实测三台到四台搬走 0.751。环加 128 个虚拟节点搬走 0.277（`docs/results/ring-bench.md`，五组两万个 key 的中位数）。

**追问**：虚拟节点数怎么选？
答：越多越均匀但环越大。实测 128 个时负载最大最小比 1.24（四台），256 个时三到四台的搬迁比例 0.253，更接近理想值。

### 路由为什么是同步 REST，交接为什么是 SQS？

**一句话答案**：worker 需要路由结果才能往下走，所以同步；交接之后 worker 不需要等审核侧，所以异步。

**展开**：同步调用有超时、有限重试和 fallback（锚点 `routing-retry`）：四次、0.2 秒起指数退避、只重试 5xx 和超时，最后进 `manual-triage`。交接放进 `rm-handoff`，Java 侧按 `(record_id, seq)` 去重（锚点 `handoff-intake`）。

**追问**：fallback 路由会不会掩盖问题？
答：会被看见：时间线上 engine 是 `fallback`，原因里列出每次失败；队列 `manual-triage` 深度也在运维页上。

### 为什么审核结论用 outbox，不在事务提交后直接发消息？

**一句话答案**：「数据库已提交」和「消息已发出」不能原子完成，outbox 让消息和结论一起提交，再由 poller 补发。

**展开**：`DecisionOutbox.add` 在结论的事务里写一行（锚点 `decision-outbox`），每半秒 flush。最坏情况是发两次；下游按 `(record_id, seq)` 写同一个 S3 key，所以两次也只有一个文件。

**追问**：poller 挂了呢？
答：未发出的行留在表里，部分索引 `decision_outbox_pending` 让扫描只碰未发的行；重启后继续发。

### 为什么 Python 和 Java 混着用？

**一句话答案**：这是按团队和组件特点分的：收件、校验、数据处理（pyarrow）在 Python 生态顺手；审核队列和审计是长期维护的业务服务，Java + Spring + Flyway 更稳。

**展开**：两边只通过契约连接：REST 的 `routing-decision.v1.json`，消息的 `handoff.v1.json`、`decision.v1.json`。Python 测「我发出去的形状完全一样」，Java 测「我回的响应没有删字段、没改类型」（锚点 `java-contract-test`）。JWT 用同一个 HS256 密钥。

**追问**：混合技术栈的成本？
答：两套构建、两套静态检查（ruff、mypy；SpotBugs），CI 里都要跑；契约测试是把两边绑在一起的那根绳子。

## 正确性和故障

### 客户端重试会不会重复处理？

**一句话答案**：不会，收件层用幂等键挡，下游每一层还各有一道去重。

**展开**：收件：`(client_id, key)` 主键。worker：`seq <= last_seq` 丢掉。Java：`handoff_inbox` 主键 `(record_id, seq)`。路由决定：`decision_id` 由 `(record_id, seq)` 派生。导出：同一个 S3 key。

**追问**：怎么证明？
答：关掉收件层保护，`test_concurrent_retries_create_exactly_one_record` 立即报 `8 records for one idempotency key`（[q07](problems.md)）。

### 消息乱序或者重复投递怎么办？

**一句话答案**：不信队列顺序，只信记录的版本号。

**展开**：`_gate`（锚点 `order-gate`）：做过的丢、下一个做、更大的放回队列一秒后再来。Java 侧任务表 `ON CONFLICT ... WHERE review_tasks.seq < EXCLUDED.seq`，迟到的旧版本改不了任何东西（锚点 `task-upsert`）。

**追问**：有一版永远不来呢？
答：后面的版本会一直等，重试次数到上限进 DLQ，运维页和 `DeadLetters` 告警会亮。这是故意的：宁可停下等人，也不乱序。

### 扩容的时候，新旧两个 worker 会同时处理一条记录吗？

**一句话答案**：Redis 锁挡住同时处理，fencing token 挡住锁过期后的迟到写入。

**展开**：拿锁时 `INCR rm:fence:<id>` 得到递增 token，`SET NX PX 15000`（锚点 `record-lock`）。提交时 `UPDATE ... WHERE fence < token`（锚点 `fenced-commit`）。测试里两个 owner 并发处理同一条记录的八个版本，同时在里面的最多一个；关掉锁变成 2（[q09](problems.md)）。

**追问**：为什么锁还不够，要 fencing？
答：锁有 TTL，worker 卡住超过 TTL 后锁被别人拿走，它醒来还会写。只有存储端校验 token 才能拒绝它。

### worker 进程崩了会怎样？

**一句话答案**：心跳六秒过期后它从环上消失，它的 key 落到顺时针下一个 worker；它队列里没确认的消息超时后重新可见。

**展开**：心跳每两秒一次（`membership.heartbeat`）。崩溃时正在处理的那一步没提交 `last_seq`，重新投递后会重做；下游各层幂等。运维页的 `WorkerDown` 告警会亮。

**追问**：重做会不会产生副作用？
答：路由决定、交接、导出都按 `(record_id, seq)` 幂等，所以重做只会多几次无害的写。

### Java 路由服务挂了会怎样？

**一句话答案**：worker 有限重试后走 fallback 队列，记录不会卡住；Java 恢复后交接消息从 SQS 里继续消费。

**展开**：重试总等待最多约 1.68 秒（含抖动），worker 不会长时间阻塞（锚点 `test-retry`）。时间线合并接口在审计不可用时返回 `audit_available: false`，页面会提示只显示了一侧。

**追问**：为什么 4xx 不重试？
答：4xx 是请求本身不对，重试只会浪费时间，立刻 fallback 并在原因里记下状态码。

### 新路由逻辑上线后出错了怎么办？

**一句话答案**：控制器每半秒看 v2 最近十秒的错误率，超过百分之五且样本够就回到 0%，并记录原因。

**展开**：判断是纯函数（锚点 `rollback-decision`），每次 v2 失败当场退回 v1，用户无感。假时钟测试里故障后 0.5 秒回滚；在跑着的系统上注入四成故障 1.7 秒回滚。关掉保护测试报 `never rolled back`（[q10](problems.md)）。

**追问**：为什么要最小样本数？
答：1% 放量时一秒可能只有一个请求，一次失败就是百分之百错误率，不设下限会频繁误回滚。

### 迁移删列跑早了会怎样？

**一句话答案**：V3 先数没回填的行，不为零就抛异常，整个迁移回滚，列不会被删。

**展开**：演示库上真的发生过：`contract blocked: 2 review_tasks rows are not backfilled`（[q03](problems.md)）。之后按「双写 → 回填到零 → 只写新列 → 删列」重来。

**追问**：回填本身有什么坑？
答：判断条件一开始把新版本的正常数据当成了脏数据，还差点抹掉新认领（[q02](problems.md)）。

## 扩展

### 流量放大十倍，瓶颈先出现在哪？

**一句话答案**：先是 worker 的处理能力和 Postgres 的写入；前者加 worker（一致性哈希只搬约 1/(N+1) 的 key），后者要看每条记录的写放大。

**展开**：每个版本大约写七到八条时间线事件、一次状态更新、一次幂等键。十倍时先把时间线改成批量写或者异步写；审核队列查询已经走 `review_tasks_queue_path` 索引（`docs/results/explain.md`）。这个仓库没做压测，以上是基于写入次数的推算，不是实测。

**追问**：dispatcher 是单点吗？
答：它只做查环和转发，无状态，可以多开几个消费同一个 SQS 队列；顺序由 worker 的版本号闸门保证，不依赖 dispatcher。

### 一百倍呢？

**一句话答案**：SQS 本身没问题，问题会变成每 worker 一个队列的管理成本和 Postgres 单库；要按 record id 分库，并让 worker 改用分片的拉取模型。

**展开**：一百倍时 worker 数量多，每 worker 一个队列难管理，可以换成 Kinesis/Kafka 按分区键分片，天然有序。Postgres 按 record id 哈希分库，和 worker 的分区对齐。时间线迁到追加型存储。

**追问**：一致性哈希还需要吗？
答：如果改用 Kafka 分区，分区到 consumer 的分配由 consumer group 负责，但「分区数固定、扩容只重分配分区」本质上是同一个思路。

### Redis 挂了会怎样？

**一句话答案**：拿不到锁，worker 会把消息放回去重试，流程暂停但不出错；状态缓存退化成直接查 Postgres。

**展开**：锁是正确性前提，所以不能「拿不到就当拿到了」。membership 也在 Redis 里，Redis 不可用时环的成员读不到，dispatcher 会认为没有活着的 worker，消息留在 intake 队列里。生产上用 Redis Sentinel 或托管的 ElastiCache 多可用区。

**追问**：fencing token 存在 Redis，Redis 丢数据会怎样？
答：token 从小重新开始，会被库里已存的大 fence 拒绝写入。要么持久化 token，要么改用 Postgres 序列生成 token。

### 审核员很多时，认领会冲突吗？

**一句话答案**：认领是一条带条件的 UPDATE，冲突时只有一个人成功，其他人拿到 409，不需要额外加锁。

**展开**：`UPDATE ... WHERE id=? AND status=?`（锚点 `claim`）。并发测试 `twoReviewersRaceForOneTaskAndExactlyOneWins`。人很多时可以改成「领下一个」接口：`FOR UPDATE SKIP LOCKED` 取队首。

**追问**：队列列表查询会不会慢？
答：走 `(queue, status, priority, created_at)` 复合索引，EXPLAIN 在两万行上是 Index Scan，没有 Seq Scan。

## 测试

### 你怎么证明它是对的？

**一句话答案**：四层：Python 单元和集成测试、Java 测试（含契约和迁移并行测试）、对跑着的整套系统的 live 测试、Playwright 从界面点一遍。

**展开**：pytest 默认用独立的测试库、测试桶、测试队列；live 测试打真实的 8890/8891。Java 用 MockMvc 加真 Postgres。e2e 包括审核流程、哈希环扩容、发布控制台、学习页的十个阶段和源码链接。数量和结果见 README。

**追问**：live 测试和单元测试会互相干扰吗？
答：数据库、桶、队列都分开；只有 live 测试碰演示环境。录屏前要先停测试。

### 「能失败的对照」是怎么设计的？

**一句话答案**：每个关键保护都有一个开关，关掉以后对应的硬核测试必须变红，打开必须变绿，两次输出都贴在 README。

**展开**：五个开关：`no_idempotency`、`modulo_hash`、`no_order_gate`、`no_lock`（Python 环境变量 `RM_LAB_SABOTAGE`），`no_rollback`（Java 系统属性）。`scripts/failing-controls.sh` 依次跑一遍。判断的是「测试是活的」：一个永远绿的测试证明不了任何事。

**追问**：开关会不会被误开到生产？
答：开关只在代码里读环境变量，生产配置不设这个变量；而且每个开关名都写在 `rmflow/lab.py` 的白名单里，拼错会直接报错。

### 契约测试防住了什么？

**一句话答案**：防住一边改了字段名或类型，另一边在运行时才发现。

**展开**：`contracts/` 里的快照两边共用。表迁移时 `task.v1.json` 是第 5 章冻结的老客户端视图，迁移每一步都和它比，字段少了或类型变了就红（锚点 `test-expand-contract`）。

**追问**：加字段算破坏吗？
答：不算。检测函数只报「删除」和「类型改变」，多出来的 `reviewer_id` 是兼容的。

### 索引设计怎么验证？

**一句话答案**：每个索引对应一条查询，用两万行种子数据跑 EXPLAIN，断言用到那个索引且没有 Seq Scan。

**展开**：`tests/test_step08_query_paths.py`（锚点 `test-explain`）。reconciler 用部分索引 `WHERE status='STORED'`，正常时几乎是空的。

**追问**：数据量小的时候 Postgres 可能选 Seq Scan，测试会不会不稳？
答：所以先灌两万行再 `ANALYZE`；没有种子数据时这个断言没有意义。

## 系统设计延伸

### 上生产还缺什么？

**一句话答案**：密钥管理、真正的身份系统、多实例的 Java 灰度状态、DLQ 重放工具、容量压测和多可用区部署。

**展开**：JWT 密钥现在来自环境变量，生产应该放 Secrets Manager 并定期轮换。灰度窗口在 Java 进程内存里，多实例时要放进共享存储或指标系统。DLQ 现在只能看，不能一键重放。没做压测，所以没有吞吐数字。

**追问**：哪一项最急？
答：DLQ 重放和告警接到值班系统。数据卡在死信里没人处理，比慢更糟。

### 换成真实的 AWS 要改什么？

**一句话答案**：代码几乎不改，改的是配置和部署：去掉 endpoint 覆盖，用 IAM 角色，S3 通知和队列用 IaC 建。

**展开**：`RM_AWS_ENDPOINT` 置空即走真实 AWS（`rmflow/aws.py`）。Lambda 连数据库要放进 VPC 并用 RDS Proxy。服务跑 ECS，Postgres 用 RDS，Redis 用 ElastiCache。Lambda 部署从 `rmflow/bootstrap.py` 改成 CDK 或 Terraform。

**追问**：LocalStack 和真实 AWS 的差别踩过吗？
答：这个仓库里没有遇到 LocalStack 特有的行为差异；踩到的 Lambda 起不来是打包问题，真实 AWS 上也会出（[q01](problems.md)）。

### 如果路由要用模型来做呢？

**一句话答案**：把模型当成 v3 引擎，同样走 feature flag 灰度和错误率回滚，再加一个离线评测集。

**展开**：`RoutingService.choose`（锚点 `flag-choose`）已经支持按记录分桶选择引擎、失败退回旧引擎。模型的「错误」不只是异常，还有路由错，需要用审核员的改派作为反馈信号。

**追问**：模型延迟高怎么办？
答：worker 侧的路由调用有超时和 fallback，超时就进 fallback 队列，不会拖住整条流水线。

### 审计记录怎么保证不被篡改？

**一句话答案**：现在是应用层只追加（代码里没有 UPDATE/DELETE 审计表的路径），生产上还要数据库权限和不可变存储。

**展开**：`AuditRepository` 只有 `append`（锚点 `audit-append`）。生产上给应用账号只授 INSERT/SELECT，定期把审计导出到开了 Object Lock 的 S3。

**追问**：为什么不用哈希链？
答：哈希链能发现篡改但不能阻止；在这个规模下数据库权限加不可变存储更直接。

## 简历对应

### 「拆成可以单独测试的组件，有明确的 REST 契约，逐步交付」怎么证明？

**一句话答案**：仓库按八个 git tag 逐步交付，每一步都能跑、测试都绿；组件之间的契约是 `contracts/` 里的快照，两边的测试都读。

**展开**：step-01 只有收件和幂等，step-04 才加 Java，step-06 做迁移，step-07 做灰度。每章教程末尾写了怎么 checkout 到那一步跑起来。

**追问**：契约变了怎么办？
答：加字段可以直接加；要删或改名就出 v2 契约，两版并存一段时间，和表迁移是同一个思路。

### 「客户端重试从不重复处理；有上限的指数重试、fallback、死信」怎么用仓库回答？

**一句话答案**：幂等在 `idempotency-guard`，重试和 fallback 在 `routing-retry`，队列层的退避和 DLQ 在 `rmflow/sqsloop.py` 和 `rmflow/bootstrap.py`。

**展开**：重试参数：四次、0.2 秒起、封顶 1.6 秒、正负百分之二十抖动。队列层：失败后可见性推迟 2 的 n 减 1 次方秒，封顶十六秒，第四次收到还失败就进 DLQ。测试：`test_poison_message_is_parked_in_the_dlq_after_bounded_retries`。

**追问**：简历上有没有数字？
答：这条没有数字。

### 「一致性哈希，扩容只搬约 1/N」怎么讲？

**一句话答案**：简历上那句是我在公司的结果；这个仓库里我自己测了：三台到四台，两万个随机 key 搬走 0.277（理想 0.25），跑着的系统上 606 个真实 id 搬走 0.2789，取模是 0.751。

**展开**：两个数字要分开讲，不能把仓库的实测当成公司的数字，也不能反过来。仓库的数字可以当场复现：`scripts/ring_bench.py`，以及页面上的扩容按钮。

**追问**：为什么是 0.277 而不是 0.25？
答：128 个虚拟节点仍有方差，新节点恰好拿到的弧长一点；256 个时是 0.253。

### 「expand/contract 迁移、feature flag、分阶段发布、按错误率自动回滚」怎么讲？

**一句话答案**：迁移在第 6 章，五个 phase，相邻两版并行测试；灰度在第 7 章，1/10/50/100 四档，错误率超过百分之五自动回到 0%。

**展开**：仓库的实测：假时钟下故障后 0.5 秒回滚，跑着的系统上 1.7 秒；迁移在演示库上真实走了一遍，并被删列守卫拦下过一次。简历上关于发布的描述是公司里的流程，这里是同一套思路的可运行版本，规模小得多。

**追问**：灰度阈值怎么定？
答：看 v1 的基线错误率再留余量；这里 v1 基本不出错，所以设了百分之五，这是演示用的值，不是推荐值。
